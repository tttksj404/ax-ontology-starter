# AX 온톨로지 스타터팩 설계 검토: 공동설계·보안감사

> 모델 신원은 이 문서로 주장하지 않습니다. 확인은 코디네이터의 modelUsage 메타데이터 몫입니다. 외부 출처는 코디네이터가 확인한 Palantir 문서 2건만 전제로 하며, 기업에 관한 사실은 만들지 않았습니다.

**판정**: 방향은 타당합니다. RAG만으로는 조직을 이해할 수 없다는 전제, 검색 전과 실행 직전의 이중 인가, 제안·승인·실행·롤백 분리, 가역 로컬 쓰기 1개 제한 모두 맞습니다. 다만 1차 산출물 정의에는 사용자가 확정한 **런타임 라우팅과 이그레스 차단**이 빠져 있습니다. **라벨 전파, 검색 부채널, 팩 거버넌스, 프로세스 전체 평가**도 정의되지 않았습니다. 아래 갭을 v1 범위에 넣어야 합니다.

## 1. 주요 갭과 최소 E2E 범위

### 1.1 갭

| # | 갭 | 위험 | v1 조치 |
|---|---|---|---|
| G1 | 단계별 평가만 있고 인계·대기·재작업·통제점 분석이 없음 | 국소 최적화, 직무분리를 무너뜨리는 권고 | 상류 상한·통제점 규칙(4.5) |

| G3 | LLM 포트만 있고 태세 라우팅·이그레스가 없음 | 기밀 근거의 외부 유출 | 라우터·가드·모의 게이트웨이 구현 |
| G4 | 라벨 부여·전파 규칙이 없음 | 요약·로그를 통한 라벨 세탁 | 필드 라벨, 무라벨=최상위, 파생물=입력 최대값 |
| G5 | 권한 필터가 검색 전인지 후인지 불명 | 전역 통계·숨김 개수로 존재 추론 | 인가 후보 안에서만 계산, 차분 테스트 |
| G6 | 도메인 팩 자체가 공격면 | 와일드카드 권한, 임의 핸들러 | 강화만 허용, 핸들러 허용목록, 2인 활성화 |
| G7 | 승인의 형식화 | 고무도장 승인 | 상태 diff·근거 표시, 검토 해시 제출 |
| G8 | 롤백 의미 미정 | 중간 변경 덮어쓰기, 통제 완화 | 보상 행동·롤백 창·중간 변경 검사 |
| G9 | 검색·답변 평가 체계 없음 | "단순하게 시작해 평가 후 확장" 불가 | 골드셋·적대 세트 CI 게이트 |
| G10 | 재사용성 미증명 | 구매 도메인이 코어에 하드코딩 | 두 번째 최소 팩, 코어 용어 검사 |

### 1.2 최소 E2E 범위

평가→온톨로지→RAG→자동화를 증명하려면 모든 계층을 얇게라도 한 번씩 관통해야 합니다.

1. `ax pack new|validate|eval`: 임의 업무용 팩 골격을 만들고 스키마·린트·코어 불변식·평가를 실행합니다.
2. `ax intake assess`: 팩 없이도 코어 기본값으로 동작하는 업무 무관 평가입니다. 결함을 넣은 합성 인테이크로 다음을 출력합니다.
   - 단계별·프로세스 모드
   - 사유와 해제 조건
   - 추가 질문과 측정 계획
3. `ax init`: 합성 소스(CSV·JSON·규정 문서)를 수집해 라벨·계보·버전을 가진 객체·링크·청크로 만듭니다. 모든 청크는 객체에 앵커됩니다.
4. `ax ask`: 엔티티 연결, 어휘 검색, 제한 순회를 모두 인가 집합 안에서 수행해 추출형 인용 답변을 냅니다. 선택적으로 라우터를 거쳐 LLM(로컬 스텁, 모의 사설 클라우드, 모의 게이트웨이)을 씁니다.
5. 행동 흐름: 결정론 탐지기(3-way match 허용오차 초과) → `ax propose` → 다른 사람의 `ax approve` → `ax execute` → `ax rollback` → `ax audit verify`.
6. 문서: 적용성·전제조건, 업그레이드 경로, 위협 모델, 운영 체크리스트, 보안태세 결정서 양식.

**유일한 쓰기**는 `ExceptionCase.open`이고 보상 행동은 `ExceptionCase.withdraw`입니다.
- 지급을 막지 않는 검토 케이스입니다.
- 대상은 1건으로 제한합니다.
- 미러된 소스 객체는 수정하지 않습니다.

**일정이 부족할 때 미루는 순서**
1. 실모델 어댑터(스텁·모의만 유지)
2. 두 번째 팩의 질의 기능

불변식, 적대 세트, 라우팅 가드는 자르지 않습니다.

### 1.3 적용성과 전제조건: 범용 원클릭 자동화가 아님

| 업무 유형 | 적합도 |
|---|---|
| 규칙이 명시되고 기록이 정형인 백오피스(구매·AP·IT서비스·인사운영) | 높음, M1~M3 |
| 문서 근거 중심의 준법·품질 기록 검토 | 중~높음, 분류·출처 품질이 좌우 |
| 개인의 권리·신용·채용·의료 판단 | 보조만(M1~M2). 개인정보보호법상 자동화된 결정 관련 권리 등 법무 검토 필요 |
| 암묵지·협상 중심 업무 | 낮음, 근거가 없으면 M1 |
| 실시간 물리·안전 제어(OT) | 범위 밖 |

업종 규제(예: 금융권 망분리, 공공 클라우드 보안인증)는 AI 티어 선택을 직접 제약합니다. 조항 해석은 도입사 법무·보안팀 몫입니다.

**전제조건**: 없으면 해당 모드 이상은 불가합니다.
- 프로세스 오너와 승인 권한자
- 역할로 매핑할 수 있는 IdP 그룹
- 3단계 이상의 분류 체계와 라벨 결정권자
- 안정 ID를 가진 소스 시스템 읽기 접근(최소한 내보내기)
- 이벤트 타임스탬프, 또는 기준선 실측 기간
- CISO·DPO가 서명한 태세 프로파일

"서버 인프라가 있다"는 전제가 IdP·KMS·이그레스 통제까지 보장하지는 않습니다. 따로 확인해야 합니다.

### 1.4 기업 AX 도입 패턴 반영 규칙

아래 패턴은 설계 가설로만 씁니다.

| 패턴 | 설계 반영 |
|---|---|
| ① 중앙 AI 게이트웨이가 승인 모델·로깅·DLP 제공 | 게이트웨이 티어 |
| ② 지식 검색 → 업무 내장 보조 → 승인형 행동으로 단계 확장 | 모드 사다리 |
| ③ 유스케이스 포트폴리오와 거버넌스 위원회 | 팩 수명주기 게이트 |
| ④ 데이터 분류 선행 | 전제조건 |

코디네이터가 1차 출처(회사 공식 발표·보고서)로 확인한 것만 증거 표(회사·URL·발행일·원문 인용·설계 매핑)에 연결합니다. 출처 없는 기업 서술은 삭제합니다.

## 2. 도메인 팩 계약·수명주기·판단 주체

### 2.1 구조

```
pack.json   id, semver, 코어 호환 범위, 산업 태그, 변경이력, 내용 해시
ontology/   object_types: 속성 타입·필수 여부·기본 라벨·계보 매핑
            link_types: 카디널리티·라벨·순회 허용·권한 부여 여부
process/    단계(입출력 타입·결정·규칙·예외·통제점), KPI 산식(이벤트 로그 기준)
intake/     필드별 질문 템플릿, 모드별 필수 필드
policy/     추상 역할, 목적, 역할×목적×타입×라벨 허용 템플릿
actions/    파라미터 스키마, 사전조건 술어, 승인 역할, 위험 등급, handler,
            보상 handler, 롤백 창, 통제완화 여부, max_targets
detectors/  결정론 규칙(허용오차 등) → 후보 행동 타입
eval/       역할별 골드 질문·기대 근거·기대 거부, 적대 케이스, 평가 픽스처
synthetic/  라벨·카나리아 문자열을 넣은 합성 데이터와 이벤트 로그
```

### 2.2 계약 규칙(검증기가 강제)

- 선언형만 허용합니다. `handler`는 코어 허용목록(`local.exception_case.open@1` 등)만 참조할 수 있습니다.
- 팩과 오버레이는 코어 안전 규칙을 **강화만** 할 수 있습니다. 차단 조건 제거, 모드 필수 필드 완화, 순회 상한 상향은 불가합니다.
- 모든 속성·링크 타입에 라벨이 필수이고, restricted에는 와일드카드 역할을 쓸 수 없습니다.
- 실행 가능한 행동은 보상 handler와 롤백 창이 필수입니다. 없으면 `executable: false`입니다.
- 권한을 부여하는 링크(예: `assigned_to`)는 권위 있는 소스 수집이나 승인된 행동으로만 생성됩니다.
- JSON Schema strict(추가 속성 금지), 경로 탈출 차단, 코드·템플릿 실행 없음.

### 2.3 바인딩·수명주기

**구성 계층**
- 팩: 업종 템플릿이며 테넌트 데이터가 없습니다.
- 테넌트 바인딩: 역할→IdP 그룹, 팩 라벨→사내 분류, 활성 목적, 태세, 읽기 커넥터를 연결합니다.
- 오버레이: 속성·규칙·임계값을 추가합니다.

팩 업그레이드는 오버레이와 3-way 병합합니다. 충돌은 보고만 하고 자동 해결하지 않습니다.

**수명주기**: 초안 → 검증 → 평가(팩 eval + 코어 적대 세트) → 2인 검토(도메인 오너 + 보안) → 해시 게시 → 바인딩 → 2인 활성화 → 모니터링 → 폐기·마이그레이션.

**버전 규칙**
- 타입·속성 제거나 의미 변경은 MAJOR, 추가는 MINOR, 질문·문서 수정은 PATCH입니다.
- 라벨 하향은 버전 등급과 무관하게 보안 승인이 필요합니다.
- 유효 정책(팩 정책 + 바인딩)이나 팩 버전이 바뀌면, 이를 묶은 미실행 제안은 무효가 됩니다.

### 2.4 판단 주체

| 결정론(코드) | LLM 보조(초안, 확인 전에는 효력 없음) | 사람 소유 |
|---|---|---|
| 인가·목적 판정, 라벨 전파, 라우팅, 모드 상한·차단, 스키마 검증, 제안 해시, 버전·멱등 검사, 인용 검증, 감사 | 인터뷰 메모→인테이크 초안, 소스 스키마→온톨로지 매핑 후보, 근거 요약, 승인 사유 문구, eval 질문·예외 분류 후보 | 행동 승인, 팩·정책·태세 변경, 미상 소스 분류와 라벨 하향, 단계별 자동화 채택, KPI 목표, 위험 수용, 공급업체 선정 같은 업무 결정 |

LLM 초안은 `provenance=llm_draft`로 저장됩니다. 사람이 확인하기 전까지 평가에서는 미상으로 취급하며, 확인할 때 확인자와 시각을 기록합니다.

### 2.5 스타터에서 도메인 심화까지의 경로

| 단계 | 내용 | 승격 게이트 |
|---|---|---|
| L0 스타터 | 합성 팩, 로컬 실행, 추출형 답변, 로컬 쓰기 1개 | CI 전체 통과 |
| L1 파일럿 | 실제 인터뷰·문서로 인테이크 작성, 바인딩, 읽기 전용 스냅샷, 오너가 작성한 골드셋, 현행 KPI 실측 | 누출 0, 재현율 기준 충족, 오너 서명 |
| L2 심화 | 예외 분류 체계, 규칙 라이브러리, 어휘 사전, 과거 사례로 탐지기 정밀도·재현율 측정, 태세별 LLM | 평가 회귀 없음 |
| L3 실제 쓰기 1개 | 섀도 모드(제안만 하고 사람이 수동 처리해 비교) → 건별 승인 실행 | 샌드박스 계약 테스트, 대상 측 멱등키, 보상 검증, 킬스위치, 커넥터 별도 승인 |
| L4 확장 | 공유 객체(공급업체 등) 거버넌스, 저위험·가역·임계 이하로 한정한 정책 자동승인과 표본 감사 | 거버넌스 위원회 승인 |

**구체적 업그레이드 방법**: 코디네이터가 확인한 문서의 "단순하게 시작하고 검색을 평가하며 확장한다"는 원칙과 같습니다.
- **검색**: 문자 n-gram BM25 → 형태소 BM25(Kiwi·MeCab-ko 계열) → 로컬 임베딩 하이브리드 → 재순위. 골드셋에서 이득이 확인될 때만 다음 단계로 올립니다.
- **PDP**: 내장 결정표에서 Cedar/OPA로 교체합니다. 같은 결정표 적합성 테스트를 통과해야 합니다.
- **모델**: 스텁 → 로컬 소형 → 사설·게이트웨이 순입니다. 티어별 구조화 출력·인용 유효성 세트를 통과해야 합니다.
- **커넥터**: 읽기 → 섀도 → 승인형 쓰기 순으로만 올립니다.

## 3. 보안 아키텍처와 불변식

### 3.1 흐름과 위협 가정

```
IdP/서명 개발토큰 → Principal{tenant, user, roles, scopes, clearance}  ※요청 본문에서 받지 않음
  + purpose(역할별 허용 목록)
  → PDP(순수 함수 → allow/deny + 사유 코드)
  → Retrieval: 인가 후보집합 → 엔티티 연결·BM25·제한 순회 → Evidence(라벨·계보·도달 경로)
  → Answer: 추출형 ─(선택)→ Router → local | private_cloud | approved_gateway | 추출형
                                     └ EgressGuard(허용목록 클라이언트만)
  → Action: Detector → ProposalBuilder → Approval → Executor(재검사) → Rollback
  → Audit(추가 전용, 해시 체인)
```

**쓰기 경로 통제**
- 업무 상태 변경은 Executor만, 소스 미러링은 Ingest만 쓰기 저장소를 import합니다. import-linter로 정적 검사합니다.
- Executor는 허용목록 handler만 실행하는 서비스 주체입니다.
- 질의 API는 읽기 전용입니다. CLI도 같은 인증·PDP를 거치며 우회 모드가 없습니다.

**가정하는 위협**
- 저권한 내부자
- 주입된 문서
- 악성이거나 오류가 있는 팩 작성자
- 타 테넌트 사용자
- 침해된 외부 모델 공급자
- 과권한 자동화 계정
- 공모한 제안자·승인자

범위 밖: 호스트 루트·DB 파일 탈취(인프라 통제 몫).

### 3.2 핵심 불변식(전부 테스트로 고정)

**인가와 가시성**
- **I1 테넌트**: 모든 행에 `tenant_id`를 두고, 저장소 호출에는 인증된 TenantContext가 필수입니다. ID는 무작위 UUID입니다. 타 테넌트 ID 조회는 미존재와 같은 응답을 받습니다.
- **I2 가시성 정의**: 가시 = 테넌트 일치 ∧ 역할×목적×타입 허용 ∧ 라벨≤인가 등급 ∧ (조직 범위 교집합 ∨ 권한 부여 링크).
  - 필드 단위로 평가합니다.
  - 그룹 소속은 IdP에서만 받습니다.
  - 권한 없음과 미존재는 같은 응답입니다.
- **I3 검색 전 인가**: 엔티티 연결·점수·순위·통계는 인가 후보 안에서만 계산합니다. SQLite FTS5의 `bm25()`는 테이블 전체 통계를 쓰므로 "단일 FTS 테이블 + 사후 필터"는 금지합니다. v1은 후보 집합 위에서 파이썬 BM25를 돌리고, 동점은 ID순으로 정렬합니다.
- **I4 순회**: 양끝 객체와 링크 타입이 모두 가시일 때만 통과합니다.
  - 기본 상한은 depth≤2, hop당 50, 총 200 노드이며 팩은 낮추기만 할 수 있습니다.
  - 숨은 이웃 수를 노출하지 않고, 집계는 가시 집합만으로 합니다.

**라벨과 목적**
- **I5 라벨**: public<internal<confidential<restricted를 사내 체계에 매핑합니다.
  - 무라벨은 restricted로 봅니다.
  - 파생물(요약·답변·로그·평가 보고서)은 입력의 최대 라벨을 받습니다.
  - 자동 경로는 라벨을 올리기만 합니다.
- **I6 목적**: 역할별 허용 목적만 선언할 수 있고, 목적은 PDP 입력·감사·제안 해시에 포함됩니다. 목적별로 AI 사용을 금지할 수 있습니다(예: `audit_review`는 추출형만).

**모델과 라우팅**
- **I7 모델과 문서는 권한이 아님**: 출력은 권한·라벨·라우팅·도구를 바꾸지 못합니다.
  - 출력 계약은 "주장마다 청크 ID + 원문 인용"입니다.
  - 인용 문자열 일치를 검증하고, 의역은 '미검증'으로 표시합니다.
  - 출력 속 객체 ID는 재인가하며, 근거 묶음 밖이면 폐기합니다.
  - v1의 LLM은 행동을 제안하지 않습니다.
- **I8 라우팅**: 근거·질문·템플릿의 최대 라벨이 허용하는 티어로만 전송하고, 허용 티어가 없으면 추출형으로 내려갑니다.
  - 상위 라벨 청크를 빼고 보내는 모드는 테넌트가 켰을 때만 쓰며, 답변에 제외 사실을 표시합니다.
  - 장애가 나도 허용 셀 밖 티어로 넘어가지 않습니다.
  - 태세 파일은 단조성을 검증합니다. 높은 라벨의 허용 티어는 낮은 라벨의 허용 티어의 부분집합이어야 합니다.

**제안·승인·실행**
- **I9 제안 불변**: 해시는 `SHA-256(JCS(RFC 8785){행동@버전, 대상+버전, 파라미터(금액은 Decimal 문자열), 예상 사전·사후 상태, 보상 명세, 근거 ID, 정책·팩 버전, 제안자, 목적, 생성·만료 시각})`입니다. 제안 수정 API는 없습니다.
- **I10 직무분리**: 승인자는 제안자와 달라야 합니다.
  - 승인자는 해당 행동의 승인 역할과 대상·근거 전부에 대한 열람 권한을 가져야 합니다. 가려진 상태의 승인은 금지합니다.
  - 승인할 때 검토한 해시를 함께 제출합니다.
  - 팩·정책·태세 변경은 서로 다른 2인이 처리합니다.
- **I11 실행 직전 재검사**: 한 `BEGIN IMMEDIATE` 트랜잭션 안에서 다음을 확인합니다.
  - 해시, 제안자·승인자의 현재 권한, 대상 버전
  - 사전조건 재평가, 정책·팩 버전, 만료, 멱등키

  확인 후 상태 CAS(`approved→executed`, 영향 행 1) → 쓰기 → 감사 순으로 진행합니다. 하나라도 실패하면 쓰기는 0건이고 거부 사유만 감사합니다.
- **I12 멱등**: `(tenant, idempotency_key)`는 유일합니다. 같은 키에 같은 내용이면 저장된 결과를 돌려주고, 다른 내용이면 409입니다.
- **I13 롤백**: 원 승인자나 행동 관리자만 요청할 수 있습니다.
  - 현재 버전이 실행 직후 버전과 같고 롤백 창 안일 때만 보상 쓰기를 합니다.
  - 중간 변경이 있으면 새 제안이 필요합니다.
  - 통제를 완화하는 롤백(예: 지급보류 해제)은 승인이 필수입니다.
  - 롤백의 롤백은 없습니다.

**감사와 실패 처리**
- **I14 감사**: 상태 변경과 같은 트랜잭션에 기록하고, 이전 해시에 연결합니다.
  - 원문 대신 ID·해시·라벨·사유 코드만 남깁니다.
  - confidential 이상 조회도 근거 ID로 기록합니다.
  - 감사 조회도 PDP를 통과해야 합니다.
- **I15 실패 시 닫힘**: PDP 오류, 라벨·태세 누락, 검증 실패는 거부나 기권으로 처리합니다. v1에는 답변 캐시가 없습니다. 도입한다면 캐시 키에 테넌트·권한 지문·목적·데이터 버전을 포함합니다.

### 3.3 보안태세별 AI 런타임

| 프로파일 | public·internal | confidential | restricted |
|---|---|---|---|
| `local_only` | local | local | local |
| `private_cloud` | private_cloud, local | private_cloud, local | local |
| `gateway_frontier` | approved_gateway, private_cloud, local | private_cloud, local | local |

셀은 허용 티어를 선호 순서로 나열한 것이며 기본값 예시일 뿐입니다. 실제 값은 테넌트가 서명으로 정합니다. 빈 셀은 추출형만 허용하고, 추출형은 언제나 허용됩니다.

| 티어 | 구성 |
|---|---|
| local | 사내 GPU의 오픈웨이트 모델을 OpenAI 호환 서버(vLLM·llama.cpp 등)로 띄우고 가중치 해시를 고정합니다. GPU가 없으면 추출형입니다. |
| private_cloud | 회사 클라우드 계정 안의 자체 호스팅, 또는 회사 계약 전용 엔드포인트(리전 고정)입니다. |
| approved_gateway | 프런티어 모델은 회사 승인 게이트웨이로만 호출하며, 공급자 직접 호출은 금지합니다. |

허용 티어가 없어도 추출형 인용 검색은 남습니다. 그래서 가장 엄격한 회사도 가치를 얻습니다. 라우팅 결정마다 티어, 모델 ID, 페이로드 라벨, 제외 청크 수, 사유를 감사합니다.

### 3.4 런타임 분류·이그레스 차단

1. 페이로드는 허용 라벨의 필드만 결정론적으로 투영합니다. NER 기반 사후 마스킹보다 이 방식을 우선합니다.
2. 질문 라벨은 테넌트 기본값에 결정론 탐지기(주민등록번호·카드·계좌·전화·이메일 패턴) 결과를 더해 정합니다. 탐지기는 라벨을 올리기만 합니다.
3. 프롬프트 템플릿도 버전과 라벨을 관리하며, 비밀을 넣지 않습니다.
4. 공급자 어댑터만 허용목록 base URL에 묶인 클라이언트를 주입받습니다. 다른 모듈의 `httpx`·`requests`·`urllib`·`socket` import는 정적 검사로 막습니다. 게이트웨이에는 라벨·목적 헤더를 보내 게이트웨이 측 정책과 이중화합니다.
5. 모델 라이브러리 오프라인 플래그(`HF_HUB_OFFLINE=1` 등)를 켜고, 분석 SDK를 금지하며, 의존성을 고정하고 SBOM을 만듭니다.
6. 테스트는 소켓 가드(pytest-socket 등)로 비허용 목적지 연결을 실패시키고, 루프백 모의 게이트웨이가 받은 페이로드에서 카나리아를 찾습니다.
7. 앱 가드는 심층 방어일 뿐입니다. 인프라 이그레스 프록시·방화벽 없이는 차단이 완결되지 않습니다.

### 3.5 감사·롤백의 한계(문서에 명시)

- SQLite 파일 관리자는 해시 체인 전체를 재작성할 수 있습니다. 외부로 주기적으로 내보낸 체인 헤드와 대조할 때만 변조가 드러납니다.
- 감사에 원문이 없으므로 조사에는 소스 시스템이 필요합니다. 시각은 앱 서버 시계를 신뢰합니다.
- 롤백은 보상 행동이지 시간여행이 아닙니다. 외부 부작용(메일 발송·지급)은 되돌릴 수 없습니다.
- 다음은 v1이 막지 못하며, IdP와 표본 감사의 몫으로 남습니다.
  - 응답 시간 부채널
  - 제안자·승인자 공모
  - 한 사람의 다중 계정

## 4. AX 우선순위 휴리스틱

### 4.1 평가 차원(서수 척도, 가중합 금지)

- **V 가치**: 처리량×건당 처리시간(둘 다 실측일 때만 수치화), 예외·재작업률, 오너가 밝힌 고충. 미상은 unknown이지 '낮음'이 아닙니다.
- **F 실현성**: 입력 정형도, 접근 경로(API·내보내기·종이), 규칙 명시성(코드·문서·암묵), 변경 빈도.
- **R 위험**: 최대 라벨, 결정 영향(금전·법·안전·개인 권리), 가역성, 규제, 통제점 여부.
- **D 준비도**: 필드 완결성, 근거 등급(관측>문서>진술), 오너 지정 여부, KPI 기준선.

### 4.2 모드 사다리

| 모드 | 내용 |
|---|---|
| M0 | 보류 |
| M1 | 인용 검색·요약 |
| M2 | 초안·추천(결정은 사람) |
| M3 | 제안-승인-실행 |
| M4 | 정책 범위 내 자동(v1 불가) |

모드는 `mode = min(R·F·D 상한, 상류 입력 품질 상한, 런타임 능력 상한)`으로 정합니다.

출력은 단일 점수가 아니라 `{mode, cap_trace, blocking_reasons, unlock_requirements, questions, measurement_plan}`입니다.

순위는 차단 항목을 뺀 뒤 사전식으로 정렬합니다. 기준은 V 높음 → R 낮음 → F 높음 → ID 순입니다. 순위는 추천일 뿐이며, 채택은 사람이 합니다.

### 4.3 차단·상한 조건(사유 코드)

| 코드 | 조건 | 결과 |
|---|---|---|
| OWNER_MISSING | 책임 오너 없음 | M0 |
| CONFLICT | 오너 간 진술 충돌 | 해소될 때까지 M0 |
| UNSTABLE | 변경 빈도가 팩 임계 초과 | M0 |
| AUTHORITY_UNKNOWN | 승인 권한자 미상 | M2 |
| IRREVERSIBLE | 비가역이고 보상 행동 미정의 | M2 |
| INDIVIDUAL_RIGHTS | 개인의 권리·신용·고용·안전 결정 | M2 + 법무 검토 |
| CONTROL_POINT | 규제·SoD 통제 결정 자체 | 결정은 M2, 근거 준비는 M3 가능 |
| SOD_COLLAPSE | 한 자동화 주체가 분리된 통제 단계를 둘 이상 수행 | 그 조합 거부 |
| UPSTREAM_QUALITY | 상류 출력 품질 미상·불량 | M2 |
| RULE_TACIT | 규칙이 진술뿐이고 문서·관측 근거 없음 | M2 |
| LABEL_UNKNOWN | 입력 라벨 미상 | restricted로 간주한 뒤 태세 적용 |

### 4.4 누락 입력 처리

- 수치 대치는 금지합니다. 기본값은 비관적으로 잡습니다.
  - 라벨 → restricted
  - 가역성 → 비가역
  - 처리량 → unknown
- 모드별 필수 필드 행렬로, 충족된 최고 모드까지만 허용합니다. 다음 모드를 여는 데 필요한 필드와 질문 템플릿을 함께 출력합니다.
- V가 unknown이면 순위에서 빼고 '정보 필요' 묶음에 둡니다.
- `as_of`를 입력으로 받아 시계 의존을 없앱니다. 같은 입력과 같은 팩 버전이면 보고서가 바이트 단위로 동일해야 합니다.

### 4.5 프로세스 전체 분석

- 이벤트 로그(없으면 기준선 실측)로 단계별 대기 비중, 재작업 루프, 인계 횟수를 계산해 병목을 표시합니다.
- 통제점 주변의 증거 수집·대조는 자동화 후보로 봅니다. 통제 결정 자체는 사람에게 남깁니다.
- 구매 예시: 요청·승인·입고 확인·지급은 서로 다른 사람이 맡는 통제입니다. 봇 계정 하나가 이 분리를 무너뜨리는 안은 SOD_COLLAPSE로 거부합니다.

### 4.6 지표(ROI 창작 금지)

- **프로세스**: 단계 리드타임 중앙값·p90, 대기시간, 예외율, 재작업률, 1회 통과율, SLA 준수율, 처리량.
- **품질·안전**
  - recall@k, 인용 충실도, 기권 정확도
  - 누출 건수(0이어야 통과하는 게이트)
  - 승인 거절률·소요시간, 롤백률, 버전 충돌률
  - 평가 모드와 오너 판단의 일치율. 불일치는 팩 규칙 개정의 입력으로 씁니다.
- **준비도**: 필드 완결성, 미상 개수, 근거 등급 분포.
- **가치 표기**
  - "기회 규모(시간/월) = 실측 처리량 × 실측 처리시간 범위"만 쓰고, 이를 '절감'이라 부르지 않습니다.
  - 금액은 회사가 준 단가가 있을 때만, 산식·입력과 함께 표시합니다.
  - 효과는 같은 측정법으로 잰 전후 차이로만 말합니다. 표본 수와 기간을 적고, 관측 범위 밖으로 외삽하지 않습니다.

### 5.2 E2E 수용 시나리오

- **E1 온보딩**: 빈 환경에서 `ax init --pack procurement-synthetic`을 실행하면 팩 검증, 합성 테넌트 적재, 준비도 보고가 이어집니다.
- **E2 평가**: 결함이 든 인테이크의 평가 결과가 골든 보고서와 바이트 동일합니다.
- **E3 질의**: "INV-0042는 왜 예외인가"라는 같은 질문에 구매담당·요청자·감사인이 서로 다른 근거 범위를 받습니다. 모든 주장의 인용이 유효합니다.
- **E4 행동**: 탐지 → 제안 → 다른 사람의 승인 → 실행 → 창 안 롤백을 거칩니다. 업무 상태는 실행 전으로 돌아가고(버전·이력 제외), 해시 체인 검증을 통과합니다.
- **E5 태세 전환**: 세 프로파일에서 E3를 반복해 기대한 라우팅과 카나리아 부재를 확인합니다.
- **E6 평가 게이트**: 다음 중 하나라도 미달이면 CI가 실패합니다.
  - 누출 0건
  - 추출형 인용 충실도 100%
  - 합성 골드셋 recall@5 ≥ 0.9(실데이터 기준은 L1에서 오너와 합의)
- **E7 재사용성**: 두 번째 최소 팩(예: IT 접근권한 요청)이 코어 수정 없이 E1~E3를 통과합니다. 코어에는 구매 도메인 용어가 0건이어야 합니다.

## 6. 트레이드오프와 운영 전 미완료 항목

### 6.1 트레이드오프

| 선택 | 이득 | 비용과 운영 대안 |

| SQLite | 단순함, 트랜잭션 | RLS·동시성 부족. 운영에서는 Postgres RLS + 외부 감사 싱크 |
| 서수·사전식 평가 | 설명 가능, 거짓 정밀도 회피 | 거칠고 인테이크 과장에 취약함. 상위 V에는 관측 근거 요구 |

### 6.2 운영 전 명시적 미완료 항목

- **인증·승인**: 실제 IdP(OIDC·SAML), 승인 시 MFA와 단계 상향 인증, 승인 위임, 금액 임계 초과 시 2인 승인.
- **데이터 저장**: Postgres RLS, HA·백업·복구, KMS 기반 저장 암호화와 키 순환, 비밀 관리, 팩 서명 키 관리.
- **네트워크**: 인프라 이그레스 통제, mTLS, 게이트웨이 계약(데이터 보존·리전·학습 사용 여부) 확인.
- **커넥터**: 실제 커넥터와 외부 보상 행동 검증, 요청·호출 속도 제한, 킬스위치.
- **검색·모델**: 대규모 ACL 인식 인덱스, 로컬 임베딩·모델 서빙, 테넌트별 모델 평가.
- **분류**: 정규식 이상의 DLP, 비정형 문서 분류를 위한 사람 검토 체계.
- **감사 운영**: WORM 감사 저장, SIEM 연동과 경보, 보존 정책과 법적 보존조치.
- **검증**: 프롬프트 인젝션 레드팀, 모의해킹, 개인정보 영향평가, 업종·국가별 규제 검토.

- **조직**: 프로세스 오너의 참여 약속, 변화관리, 교육. 이것 없이는 기술이 완성돼도 "자동화 완료"라고 부르지 않습니다.
